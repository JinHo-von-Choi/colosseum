Colosseum은 논쟁이 있는 질문을 여러 AI 에이전트가 따로 검토하게 하고, 검증된 근거를 통과한 결론만 남기는 에이전트 스킬이다.

Claude Code, Antigravity처럼 스킬을 읽어 들이는 에이전트 호스트에서 돌아간다. Claude Code 플러그인으로 설치하면 워크플로, 훅, 전용 참가자 에이전트까지 쓰고, 다른 호스트에서는 같은 절차를 스크립트로 진행한다.

주장을 팩트체크하거나, 라이브러리, 아키텍처, 운영 방식 같은 기술 선택지를 비교하거나, 설계 검토에 붙일 결정 기록이 필요할 때 쓴다. 단순 검색, 요약, 번역, 코드 작성에는 쓰지 않는다.

## 동작 방식

1. 자료(파일, 디렉터리, URL, 붙여 넣은 글)를 지정하면 모든 참가자가 그 자료부터 읽는다. 그래서 일반론이 아니라 사용자의 상황을 두고 토론한다.
2. 참가자들이 서로의 답을 보지 않고 각자 초안을 쓴다.
3. 토론 전에 초안들의 투표 결과와 풀링 확률을 기록한다. 이것이 기준선이다.
4. 참가자들은 결론을 좌우하는 주장을 공격한다. 사실 공격에는 URL과 원문 인용이 있어야 하고, 인용은 실제 페이지와 대조한다.
5. 주장, 근거, 공격 관계로 판정 엔진이 결론을 계산한다. 같은 입력이면 늘 같은 결과가 나온다. 검증된 근거, 반박 실패, 독립 배심원의 동의가 모두 있어야 기준선과 다른 결론을 낸다.
6. 보고서에는 기준선, 라운드별 전개, 출처별 대조 결과, 남은 쟁점이 들어간다. 결론이 갈리면 합의로 포장하지 않고 조건부 답으로 쓴다.

참가자는 서로 다른 모델 계열에서 올 수 있다. 사용자 컴퓨터에 설치된 AI 에이전트 CLI(Codex, Gemini CLI, Kimi Code, MiniMax Code, OpenCode, Hermes Agent, OpenClaw 등)를 찾아 호스트의 기본 모델과 함께 쓴다.

## 빠른 시작

Claude Code에서는 플러그인 마켓플레이스로 설치한다.

```
/plugin marketplace add JinHo-von-Choi/colosseum
/plugin install colosseum@colosseum
```

호출어를 넣어 질문한다.

```
colosseum: 우리 팀의 REST 폴링을 메시지 큐로 바꿔야 할까?
```

```
팩트체크 해줘: 인간은 하루 물 8잔을 꼭 마셔야 한다
```

호출어: `colosseum`, `팩트체크`, `AI 토론`, `여러 AI에게 물어봐`, `비판적으로 분석`, `다양한 관점`

사용자 자료를 근거로 검토하게 하려면 요청에 자료를 적는다.

```
colosseum: docs/queue-proposal.md와 src/poller/ 읽고, 큐를 도입할지 판단해 줘
```

특정 에이전트를 쓰려면 이름을 적는다. 예: "colosseum, codex랑 kimi로 검토해 줘: ..."

## 결과물

- 보고서: 블라인드 초안의 입장, 투표 기준선(`BASELINE_VOTE`, `P0`), 라운드별 전개, 충돌 판정, 반대 입장의 가장 강한 논거, 미해결 쟁점의 조건부 답, 최종 답과 `P_final`(UNCALIBRATED 표시), 출처별 인용 대조 결과, 증거 품질 점검표
- 결정 기록: 의사결정과 기술 질문이면 ADR 형식의 `decision.md`와 `decision.json`을 만든다. 추천안과 적용 조건, 결정적 근거 3개 이내, 가장 강한 미해결 반론, 다음 확인 항목, 검토의 한계가 들어간다.
- 가정 바꿔 보기: "출처 E3를 빼면 어떻게 되나?" 같은 질문에 모델을 다시 부르지 않고 판정을 재계산해, 무엇이 왜 바뀌는지 보여 준다.

## 요구 사항

| 필요한 것 | 용도 |
|----------|------|
| 스킬을 읽어 들이고 웹 검색 도구가 있는 에이전트 호스트 | 근거 수집 |
| 페이지 가져오기 도구 | 인용을 페이지 원문과 대조. 없으면 검색 스니펫으로만 대조한다 |
| Python 3.9 이상 | 실행 관리와 판정 계산. 없으면 같은 절차를 수동으로 따르고 그 사실을 보고서에 적는다 |
| 다른 AI 에이전트 CLI(선택) | 다른 모델 계열의 참가자 |

Linux에서 시험했다. `fcntl`이 없는 시스템에서는 스크립트가 실행을 시작하지 않는다.

## 한계

- 시험을 마친 호스트는 Claude Code다. 다른 호스트에서는 워크플로와 훅 없이 돌기 때문에, 예산 상한과 블라인드 초안 격리는 호스트가 스킬 지시를 따르는지에 달려 있다.

- 인용은 페이지 가져오기 도구가 돌려준 텍스트와 대조한다. 이 텍스트도 모델이 만든다. 검증된 인용은 강한 근거지만 증명은 아니다.
- 외부 에이전트는 사실 기반과 전달받은 인용만 보고 논쟁하며, 토론 중에 직접 검색하지 않는다. Claude 참가자는 직접 검색한다.
- 실행 한 번에 라운드 3회, 검색 25회, 페이지 가져오기 15회가 상한이다.
- 예측과 추정 질문은 실험 단계다. 아이디어 생성은 다루지 않는다.
- 확률은 보정되지 않았다.

## 스킬로만 설치

다른 호스트에서 쓰거나, Claude Code에서 플러그인 없이 쓸 때:

```bash
git clone https://github.com/JinHo-von-Choi/colosseum
cd colosseum && ./install.sh
```

스킬을 `~/.claude/skills/colosseum`에 링크한다. 다른 호스트라면 그 호스트의 스킬 디렉터리를 지정한다.

```bash
COLOSSEUM_INSTALL_DEST=<호스트 스킬 디렉터리>/colosseum ./install.sh
```

이 방식에서는 훅, 워크플로, 플러그인 에이전트가 없고, 같은 절차를 스크립트로 진행한다. 버전을 고정하려면 실행 전에 원하는 태그를 체크아웃한다. 설치 스크립트는 자기가 만들지 않은 파일이나 링크를 덮어쓰지 않는다.
