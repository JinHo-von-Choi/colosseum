# 프로토콜 상세

SKILL.md의 핵심 규칙과 실행 흐름을 단계별로 풀어 쓴 문서다. 스크립트를 쓸 수 없는 환경에서는 이 문서의 절차를 중재자가 손으로 수행한다.

참가자 출력은 [formats.md](formats.md)의 JSON 턴 형식을 따른다. 아래 프롬프트의 "출력 형식" 항목은 그 JSON 필드와 일대일로 대응한다.

---

## 0. 구성 요소

| 구성 요소 | 담당 | 비고 |
|----------|------|------|
| 중재자 | Claude 본체 | 진행, 검색 대행, 인용 검증, 기록, 판정 |
| 참가자 | 외부 AI CLI 또는 Claude 서브에이전트 | 기본 3명, 익명 라벨 |
| 배심원 | Claude가 아닌 CLI 1개, 없으면 새 Claude 서브에이전트 | Phase 4 충돌 판정, 역전 동의 |
| 사전부검자 | 초안이 가장 달랐던 참가자 또는 배심원 | Phase 4 최종안 점검 |

## 1. 실행 전제조건

### 1.1 웹검색 도구

다음 중 사용 가능한 것을 `SEARCH`로 정한다.

1. Brave Search MCP 도구 (`mcp__<서버명>__brave_web_search` 형태)
2. Claude Code 내장 `WebSearch`

둘 다 없으면 폐쇄형 점검 모드로 강등한다. 모든 팩트 클레임에 "미검증"을 붙이고, P_final은 0.3~0.7 범위로 제한하며, 결과 머리에 "검색 없음: 검증되지 않은 답"이라고 명시한다.

페이지 대조에는 `WebFetch`를 쓴다. 없으면 인용은 모두 u가 되므로, 결과에 "인용 대조 불가"를 명시한다.

### 1.2 외부 AI 에이전트 탐지

`scripts/agents.json` 등록부에 있는 에이전트 CLI 중 PATH에 설치된 것을 찾는다.

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/relay.py" --data "${CLAUDE_PLUGIN_DATA}" detect --probe
```

`--probe`는 에이전트마다 한 단어 시험 프롬프트를 보내, 설치되어 있어도 로그인이나 설정이 안 되어 응답하지 않는 것을 걸러 낸다. 결과는 24시간 재사용한다(`--refresh`로 다시 확인).

| id | 도구 | 기본 계열 | 프롬프트 전달 |
|----|------|----------|--------------|
| codex | OpenAI Codex CLI (`codex exec`, 읽기 전용 샌드박스) | openai | 표준입력 |
| gemini | Gemini CLI | google | 표준입력 |
| kimi | Kimi Code CLI (`kimi -p`) | moonshot | 인자 |
| mcode | MiniMax Code (`mcode exec`) | minimax | 인자 |
| qwen | Qwen Code | alibaba | 표준입력 |
| opencode | OpenCode (`opencode run`) | 설정한 모델에 따름 | 인자 |
| hermes | Hermes Agent (`hermes -z`) | 설정한 모델에 따름 | 인자 |
| openclaw | OpenClaw (`openclaw agent --agent main --message`) | 설정한 모델에 따름 | 인자 |
| cursor-agent, copilot, crush, amp, goose | 각 CLI의 비대화형 모드 (문서 미검증, probe로 확인) | 설정에 따름 | 인자 또는 표준입력 |
| llm, aichat, ollama | 범용 모델 CLI (ollama는 모델 이름 설정 필요) | 설정에 따름 | 표준입력 |
| claude | Claude Code CLI (`claude -p`, 쓰기 도구 차단) | claude | 표준입력 |

여러 모델을 고를 수 있는 에이전트(opencode, hermes, openclaw 등)는 실제 모델 계열을 알 수 없으므로 명단 결과에 "계열 추정"으로 표시된다. 사용자 파일에서 `family`를 실제 모델 제공자로 고치면 계열 가중 투표가 정확해진다.

첫 호출에서 실패하거나, 초안 형식을 두 번 연속 지키지 못한 에이전트는 명단에서 빼고 Claude 서브에이전트로 대체한다. 제외 사실은 메타 정보에 남긴다.

### 1.3 참가자 명단

`relay.py roster`가 정한다.

1. 사용자가 지정한 에이전트(`--prefer`, 또는 그것만 쓰는 `--only`)를 지정한 순서대로 먼저 넣는다. 사용자 파일의 `prefer`와 환경변수 `COLOSSEUM_AGENTS`도 같은 효과다.
2. 남은 자리는 설치되어 응답하는 에이전트를 우선순위 순서로 채우되, 이미 들어간 모델 계열은 건너뛴다(사용자가 직접 지정한 경우는 예외).
3. 외부 에이전트는 기본 2자리까지다. 한 자리는 검색을 직접 하는 Claude 참가자에게 남긴다. 외부 에이전트가 없으면 Claude 참가자 3명이고 "동종 명단"으로 표기한다.
4. Claude Code CLI는 내장 Claude 참가자와 같은 계열이므로 사용자가 지정할 때만 넣는다.
5. 명단에 들지 않은 에이전트 중 명단에 없는 계열의 것을 배심원(`cli_juror`)으로 쓴다.
6. 라벨 A, B, C는 무작위 순서로 붙는다.

---------|-----------|
| 0개 | Claude 서브에이전트 3명. "동종 명단" 표기 |
| 1개 | CLI 1 + Claude 서브에이전트 2 |
| 2개 이상 | CLI 2 + Claude 서브에이전트 1 (사용자가 지정한 CLI 우선, 없으면 탐지 순서) |

Claude 서브에이전트끼리는 모델 계열이 같아 오류도 비슷하게 난다. 그래서 참가자마다 검색 출발점을 다르게 준다.

```
참가자 1: 주장을 지지하는 근거부터 찾는다
참가자 2: 주장을 반박하는 근거부터 찾는다
참가자 3: 1차 자료(공식 통계, 원 논문, 법령, 공식 문서)부터 찾는다
```

관점 페르소나(회의론자, 실용주의자, 현실주의자)는 보조 수단으로만 붙인다. 역할극으로 만든 반대는 진짜 이견을 대신하지 못한다.

서브에이전트 모델은 고정 ID가 아니라 별칭으로 지정한다. 참가자는 세션 기본 모델을 쓰고, 인용 대조처럼 기계적인 단계는 `haiku`로 돌린다.

## 2. 호출 방법

### 2.1 Claude 서브에이전트

- Agent 도구(subagent_type: general-purpose)로 호출한다. 같은 단계의 참가자는 한 메시지에서 병렬로 호출해 서로의 출력을 보지 못하게 한다.
- 참가자 프롬프트에는 "다른 참가자에게 메시지를 보내거나 새 에이전트를 띄우지 마라"를 넣는다.
- 참가자에게는 그 단계에 필요한 정보만 준다. Phase 3에서는 자기 주장을 겨냥한 공격과 증거, 그리고 익명화한 중립 요약만 준다. 전체 기록은 중재자만 본다.
- 발언 한 번은 300단어 이하로 제한한다.

### 2.2 외부 에이전트 호출

프롬프트는 셸 명령에 넣지 않는다. heredoc 종료자, `$( )`, 따옴표, 줄바꿈이 프롬프트에 들어 있으면 셸 템플릿 밖으로 빠져나올 수 있기 때문이다. `scripts/relay.py`가 등록부의 고정 인자 배열로 실행한다.

1. `python3 "${CLAUDE_SKILL_DIR}/scripts/relay.py" mktemp`로 전용 디렉터리(0700)를 만든다.
2. Write 도구로 프롬프트 전문을 그 디렉터리의 `prompt.txt`에 쓴다.
3. 실행한다.

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/relay.py" run --cli <id> --prompt-file "<dir>/prompt.txt" --timeout 180 --cleanup
```

- 등록부에 없는 id나 설치되지 않은 에이전트는 실행 전에 실패한다.
- 표준입력 방식 에이전트는 프롬프트를 표준입력으로 받는다. 인자 방식 에이전트는 프롬프트를 인자 하나로 받는다(셸을 거치지 않음). `-`로 시작하는 프롬프트는 옵션으로 읽히지 않도록 앞에 공백 하나를 붙인다.
- 에이전트는 빈 전용 작업 디렉터리에서 실행되므로 코딩 에이전트라도 사용자의 저장소를 고칠 수 없다. 가능한 경우 읽기 전용 모드로 실행한다(codex 읽기 전용 샌드박스, claude 쓰기 도구 차단).
- 시간 초과 시 에이전트의 프로세스 그룹 전체를 종료하고, 출력은 200,000바이트에서 자르며, `--cleanup`으로 프롬프트 디렉터리를 지운다. relay 자체가 중단되어도 에이전트 프로세스를 함께 종료한다.
- 결과 JSON의 `ok`가 false이거나 `timed_out`이 true면 그 단계의 발언 없음으로 기록한다.
- 사용자 질문과 토론 프롬프트는 그 에이전트의 모델 제공자에게 전송된다. 설치되어 있다는 이유만으로 사용자 몰래 넣지 않는다. 실행 계획에 제공자와 전송 범위를 보이고, 사용자가 원하지 않으면 외부 에이전트 없이 진행한다. 민감한 저장소 내용이나 개인정보는 사용자가 승인한 범위에서만 보낸다.

사용자 정의: `<data>/agents.json`(또는 `COLOSSEUM_AGENTS_FILE`)에 같은 형식으로 쓰면 등록부를 덮어쓴다.

```json
{
  "prefer": ["kimi", "codex"],
  "agents": {
    "opencode": {"family": "zhipu", "family_uncertain": false},
    "ollama": {"vars": {"model": "qwen3"}},
    "gemini": {"disabled": true},
    "my-agent": {"name": "My agent", "provider": "Mistral", "family": "mistral",
                 "argv": ["my-agent", "--ask", "{prompt}"], "prompt": "arg"}
  }
}
```

`argv`의 첫 원소는 실행 파일 이름이고, `{prompt}`는 인자 방식일 때 프롬프트가 들어갈 자리, 다른 `{이름}`은 `vars` 값이다. 자리표시자는 인자 전체여야 한다(`--q={prompt}` 형태는 거부).

### 2.3 CLI 참가자의 검색 대행

외부 CLI는 `SEARCH`를 호출할 수 없으므로 두 단계로 진행한다.

```
1단계: CLI가 필요한 검색 질의를 SEARCH_QUERIES에 최대 2개 적는다
2단계: 중재자가 질의를 실행하고 상위 결과의 제목, URL, 검색 엔진 스니펫을 가공 없이 그대로 붙여 CLI를 다시 호출한다
```

중재자는 요지를 요약하거나 결과를 고르지 않는다. 같은 질의는 세션 캐시로 한 번만 실행한다.

```
[Prime Directive]

모든 팩트 클레임에는 URL과 50단어 이하 원문 인용을 붙여라. 원문에 없는 문장을 인용으로 만들지 마라.
```

## Phase 0: 문제 파싱

```
QUESTION   : [원본 질문]
TYPE       : [factual / technical / decision / normative / forecast / estimate / diagnostic / creative]
STAKES     : [low / medium / high]
AS_OF      : [기준 시점. 시간에 민감한 질문이면 명시]
SEARCH_KW  : [초기 검색 키워드 3-5개]
DEBATE_AX  : [무엇이 충돌할 수 있는가]
ROSTER     : [참가자 명단, 호출 방식, 동종 명단 여부]
BUDGET     : 검색 25 (Phase 1 3, 라운드당 4, 최종 감사 예비 5) / 페이지 가져오기 15
```

TYPE이 factual이고 Phase 1만으로 답이 확정되면 토론을 생략하고 팩트 베이스 기반 답만 낸다. 확정 조건은 서로 다른 원출처 2곳 이상의 v 인용이 일치하고, 반대 근거가 없는 것이다. 같은 통신 기사나 보도자료를 옮겨 실은 URL 여러 개는 원출처 하나로 센다. 종료 사유는 "토론 불필요"로 기록한다. 이때도 출력 형식은 그대로 쓰되, 기준선 절에는 `BASELINE_VOTE: 해당 없음(토론 불필요)`을 적는다.

TYPE이 decision, normative, forecast, estimate, diagnostic, creative이면 [modes.md](modes.md)의 해당 절차를 따른다. 이 문서의 Phase 1~4는 factual과 technical의 절차이며, decision과 normative는 여기에 modes.md의 단계를 더한다.

## Phase 0.5: 사용자 자료

사용자가 자료(파일, 디렉터리, URL, 붙여 넣은 글)를 지정했으면 `CTL materials add`로 실행에 고정하고, 사실 기반 검색보다 먼저 읽는다.

1. 자료마다 질문과 관련된 요약(150단어 이내)과 판단에 쓸 원문 구절(50단어 이하, 최대 8개, 위치 표시)을 만든다.
2. 이 요약을 `[사용자 자료]` 블록으로 모든 참가자 프롬프트의 맨 앞에 넣는다. 참가자는 일반론이 아니라 자료 내용에 근거해 논의하고, 자료와 다른 주장에는 따로 근거를 댄다.
3. 파일과 붙여 넣은 글은 url을 `material:M1`처럼 써서 인용한다. 웹 자료는 원래 URL로 인용한다.
4. 사실 기반 검색은 자료가 답하지 않거나 자료와 어긋나는 공개 근거를 우선 찾는다.
5. `CTL verdict`가 `material:` 인용을 고정된 사본과 다시 대조한다.

## Phase 1: 초기 팩트 그라운딩

중재자가 `SEARCH`를 3회 실행한다. 각도는 서로 달라야 한다: 찬성 근거, 반대 근거, 최신 현황. 논쟁적인 공적 주장이면 기존 팩트체크 기사부터 찾는다. 판정에 중요한 상위 결과 2~3개는 `WebFetch`로 가져와 인용을 확보한다.

인용 레코드 형식:

```
[F1] URL: ... | 발행처: ... | 발행일: ... | 조회일: ...
     인용: "원문 그대로 50단어 이하" | 대조: [v / n / u / 스니펫]
     원출처: [같은 원 보도, 보도자료, 데이터셋이면 같은 ID] | 신뢰도: [high/medium/low]
```

신뢰도 기준: high는 1차 자료, 공식 문서, 동료 심사 연구. medium은 주요 언론, 전문가 블로그. low는 커뮤니티 글, 출처 불명 요약. 중계 매체의 신뢰도는 중계 매체와 원출처 중 낮은 쪽으로 정한다.

## Phase 2: 블라인드 초안

모든 참가자가 동시에, 서로 모르는 상태에서 쓴다.

```
[Prime Directive]

다음 질문에 대한 입장을 명확히 선언하라. 다른 참가자의 입장은 공개되지 않는다.
[검색 출발점과 보조 관점, 있으면]

[QUESTION]
기준 시점: [AS_OF]
참고 팩트: [FACT_BASE]

FACT_BASE 밖의 근거가 필요하면 직접 검색하라(최대 2회).
(CLI 참가자: 필요한 질의를 SEARCH_QUERIES에 적어라.)

출력 형식:
- POSITION: [핵심 주장 1문장, 구체적 입장]
- CLAIMS: [팩트 클레임 2-4개. 각각 "주장 | URL | 원문 인용(50단어 이하)"]
- KEY_ASSUMPTIONS: [입장이 성립하려면 참이어야 하는 가정 최대 3개, 각각 거짓이면 무엇이 바뀌는지]
- CRUXES: [이것을 달리 믿게 되면 입장을 바꾸겠다는 명제 최대 2개, 각각 경험적/가치 표시]
- STRONGEST_COUNTER: [내 입장에 대한 가장 강한 반론 1개]
- PROBABILITY: [내 POSITION이 옳을 확률, 0.02-0.98]
```

진행:

1. Claude 참가자는 병렬 호출, CLI 참가자는 2.3 절차를 거친다.
2. 전원 제출 뒤 중재자가 모든 CLAIMS의 인용을 대조한다(아래 인용 대조 절차).
3. 초안을 익명 라벨로 바꿔 기록한다. PROBABILITY는 기록만 하고 다른 참가자에게 보이지 않는다.

### 인용 대조 절차 (모든 단계 공통)

1. 인용이 붙은 URL을 `WebFetch`로 가져오며, 프롬프트는 "다음 구절이나 거의 같은 구절이 페이지에 있으면 그 구절과, 그 구절이 든 문장 전체 및 앞뒤 한 문장을 원문 그대로 반환하고, 없으면 NOT FOUND라고만 답하라: [인용]"으로 한다.
2. 반환된 텍스트와 인용을 `CTL quote --stdin`으로 분류한다(matcher `quote-match/2`). 공백, 유니코드 호환 문자, 따옴표, 대시와 마이너스 기호, 대소문자, Markdown 표기만 정규화하고, 부호, 숫자, 단위, 부정어, 비교 표현은 그대로 둔다.
   - v: 인용이 원문의 연속 구간과 일치하고, 그 문장에서 인용이 뺀 부분에 조건이나 범위를 정하는 말(if, unless, only, except, 경우, -면, -때 등)이 없다.
   - n: 검토 필요. 일부 단어만 다른 근접 일치이거나, 원문 그대로지만 같은 문장의 조건절을 뺀 인용이다. 검증된 증거로 세지 않는다. 사람이 원문을 보고 확인하기 전까지 가중치 0이다.
   - u: 원문에 없다. 부정어 삭제, 부호 변경(-5.2%를 5.2%나 +5.2%로), 이상과 미만 같은 비교 전환은 근접 일치가 아니라 u다.
   모델이 의미가 같다고 판단해도 문자열 대조 등급을 올리지 않는다.
3. 유료 장벽이나 차단으로 가져오지 못하면 같은 원출처의 공개 사본을 한 번 찾는다. 그래도 없으면 u다.
4. 지지 판정(support)은 인용 대조와 별개로, 주장 하나와 인용 및 그 문맥만 보고 한다: full, partial, none, 판단 불가면 unknown. 같은 인용이 다른 주장에 쓰이면 원문 획득은 재사용하되 지지 판정은 주장마다 새로 한다.
5. 대조 결과는 인용 옆에 표시한다. u 인용은 판정 근거에서 빼고 별도 목록으로만 보여 준다. n 인용은 "검토 필요" 목록에 둔다.
6. 근거 자격: 대조 결과가 v(또는 스니펫 수준 검증의 snippet)이고, support가 full이나 partial이며, 출처가 superseded가 아닌 증거만 점수와 "검증된 증거" 자격을 갖는다. 점수와 undercut 예외는 같은 자격 규칙을 쓴다.

대조는 판정을 좌우하는 인용부터 한다. 페이지 가져오기 상한에 닿으면 남은 인용은 "예산상 미확인"으로 표시한다.

원문 대조 불가 모드: 서로 다른 도메인에 대한 가져오기가 연속 3회 실패하면, 네트워크나 도구 환경의 문제로 보고 이 모드로 전환한다. 이후 가져오기는 시도하지 않는다. 검색 결과에서 실제로 돌아온 스니펫 텍스트를 인용과 대조해, 원문 그대로 들어 있을 때만 "snippet"으로 분류한다. 검색 도구나 모델이 "들어 있다"고 답한 것만으로는 인정하지 않는다. 스니펫에 없으면 u다. 증거마다 획득 방식(full_page, snippet, unavailable)을 기록하고, 결과 머리에는 그 건수를 적는다. 일부 증거만 스니펫이면 "원문 대조"라고 쓰지 않는다. 전부 스니펫이면 "원문 대조 불가: 스니펫 수준 검증"을 명시하고, 역전 규칙의 v 재확인 조건은 서로 다른 원출처 2곳의 스니펫 일치로 대신한다. 토론은 이 모드에서도 정상 진행한다.

## Phase 2a: 기준선

초안이 모이면 토론 전에 기준선을 계산해 기록한다.

1. 입장 묶기: 의미가 같은 POSITION끼리 묶는다.
2. 계열 가중 투표: 같은 모델 계열의 참가자들은 합쳐서 1표로 센다(계열 안에서 다수인 입장이 그 계열의 표). 결과를 BASELINE_VOTE로 기록한다.
3. 풀링 확률 P0: 다수 입장에 대한 각 참가자의 확률을 구하고(다수 입장 참가자는 PROBABILITY, 반대 입장 참가자는 1 - PROBABILITY), 로그오즈 평균으로 합친다. 입장 묶음이 셋 이상이면 1 - PROBABILITY는 나머지 입장 전체의 확률이므로 다른 입장 수(k - 1)로 나눠 쓰고, 결과에 그 방식을 적는다(`p0_method`). 이때 P0를 이항 확률처럼 "나머지는 1 - P0"로 표시하지 않는다.

```bash
python3 -c "import math,sys;p=[min(.98,max(.02,float(x))) for x in sys.argv[1:]];m=sum(math.log(x/(1-x)) for x in p)/len(p);print(round(1/(1+math.exp(-m)),3))" 0.8 0.7 0.35
```

Bash를 쓸 수 없으면 같은 식(각 확률을 0.02~0.98로 자른 뒤 ln(p/(1-p))의 평균 m을 구하고 1/(1+e^(-m)))을 직접 계산하고 계산 과정을 기록한다.

토론 생략 조건(모두 충족):

- 모든 초안의 POSITION이 같은 묶음이다
- 명단이 동종이 아니다
- 모든 PROBABILITY가 0.8 이상이다
- 근거 자격(v, support full/partial)을 갖춘 인용으로 뒷받침되는 STRONGEST_COUNTER가 없다

토론을 생략해도 Phase 4의 사전부검(4.3)과 증거 품질 점검표(4.4)는 반드시 수행한다.

동종 명단이 만장일치이면 바로 받아들이지 않는다. 토론에 참여하지 않은 새 서브에이전트 1명에게 "가장 강한 반대 증거를 v 인용과 함께 찾아라"를 한 번 맡긴다. 검증된 반대 증거가 나오면 Phase 3으로 간다.

## Phase 2b: 쟁점 지도

1. 초안들의 CRUXES와 CLAIMS를 대조해 쟁점을 만든다. 우선순위는 더블 크럭스다. 즉 한쪽 입장은 그것이 참이어야, 다른 쪽 입장은 거짓이어야 성립하는 명제다.
2. 경험적 쟁점에는 양측이 "검색이 X를 보이면 입장을 옮기겠다"는 한 줄 약속을 먼저 쓴다. 중재자가 합의된 질의를 먼저 실행하고 결과를 양측에 준다.
3. 가치 쟁점은 토론하지 않고 "X를 Y보다 중시하면 A, 아니면 B"라는 조건부 답으로 보낸다.
4. 쟁점 해소가 원래 질문의 답을 바꾸지 않으면 목록에서 뺀다.

충돌 수를 C0로 기록한다. C0 = 0이면 Phase 4로 간다.

## Phase 3: 증거 라운드 (기본 1, 상한 3)

### 3.1 역할 배정

매 라운드 미해소 쟁점 중 판정 영향이 가장 큰 1개(STAKES high면 최대 2개)를 고른다.

```
변호인 (Defender)         : 공격받는 주장을 가진 참가자
검사 (Prosecutor)         : 그 주장과 가장 정면으로 대립하는 참가자
반대증인 (Adverse Witness): 초안이 양 당사자와 가장 달랐던 참가자. 같다면 라운드마다 돌아가며 맡는다
```

### 3.2 라운드 구조

ATTACK 단계 (검사와 반대증인은 병렬 호출):

```
[검사 프롬프트]
[Prime Directive]
먼저 변호인의 주장과 최선의 근거를 3문장 이내로 공정하게 재진술하라(STEELMAN).
그다음 검증 가능한 클레임 하나를 골라 직접 검색해 반박하라. 추측 비판은 금지다.

[변호인 POSITION과 CLAIMS, 익명 라벨]

출력 형식:
- STEELMAN: [3문장 이내]
- TARGET_CLAIM: [반박 대상]
- EVIDENCE: [URL | 원문 인용 50단어 이하]
- ATTACK: [반박 또는 부분 인정, 300단어 이하]
- POSITION_UPDATE: [검색 결과로 내 입장이 바뀌었으면 수정본과 그 증거, 아니면 "유지"]
```

```
[반대증인 프롬프트]
[Prime Directive]
양측이 공유하지만 검증하지 않은 전제 하나를 골라 검색으로 확인하라. 어느 쪽도 편들지 마라.

[양측 POSITION, CLAIMS, KEY_ASSUMPTIONS, 익명 라벨]

출력 형식:
- PREMISE: [검증 대상 전제]
- EVIDENCE: [URL | 원문 인용 50단어 이하]
- VERDICT: [성립 / 불성립 / 부분 성립]
- IF_FALSE: [전제가 거짓이면 무너지는 입장]
```

중재자는 공격과 전제 검증의 인용을 대조한 뒤 DEFEND 단계로 넘긴다.

DEFEND 단계:

```
[변호인 프롬프트]
[Prime Directive]
먼저 검사의 STEELMAN이 당신 주장을 공정하게 옮겼는지 판정하라(충실 / 왜곡).
이어 검사의 공격과 반대증인의 지적에 응답하라. 각 인용 옆의 대조 결과(v/n/u)와 지지 판정을 참고하라.
- 공격이 근거 자격을 갖춘 증거(v 또는 snippet, support full/partial)에 기반하면 인정하고 POSITION을 수정하라. n(검토 필요)과 u 인용은 인정 근거가 아니다
- 공격이 약하거나 u 인용에 기대면 검색 근거로 반박하라
- 부분적으로 맞으면 그 범위를 명시하라

출력 형식:
- STEELMAN_CHECK: [충실 / 왜곡, 왜곡이면 한 줄 이유]
- RESPONSE: [인정 / 반박 / 부분 인정, 300단어 이하]
- EVIDENCE: [반박 시 필수. URL | 원문 인용]
- POSITION: [갱신된 입장]
- CHANGE_BASIS: [입장을 바꿨다면 근거가 된 증거 ID 또는 논리 오류 이름, 아니면 "변경 없음"]
```

STEELMAN_CHECK가 "왜곡"이면 그 공격은 무효로 기록한다. 중재자가 보기에 변호인의 왜곡 판정이 명백히 부당하면 그 사실도 함께 기록한다.

## Phase 4: 판정

### 4.1 충돌 판정

각 미해소 쟁점을 배심원이 판정한다.

- 배심원은 Claude가 아닌 CLI를 우선한다(참가자로 쓰지 않은 CLI가 있으면 그것, 없으면 참가자 CLI 중 하나). CLI가 없으면 토론에 참여하지 않은 새 Claude 서브에이전트가 맡고, 결과에 "동종 배심원"을 표기한다.
- 배심원에게는 익명 라벨, 양측 주장, 근거 자격을 갖춘 인용만 준다. n과 u 인용은 "미확인 인용"으로 따로 보여 주고 증거로 쓰지 말라고 지시한다.
- 같은 쟁점을 양측 제시 순서를 바꿔 두 번 판정한다. 두 판정이 다르면 "판정 불가(순서 민감)"로 기록한다.
- 판정 라벨: A 우세 / B 우세 / 쌍방 부분 인정 / 조건부 / A 반박됨·B 미입증

"A 반박됨·B 미입증"은 한쪽이 반박되었다고 다른 쪽이 입증된 것은 아닐 때 쓴다.

### 4.2 합성과 역전 규칙

```
최종안 초안 = 증거에 근거한 인정 + 판정에서 우세한 측의 논거 + 조건부 쟁점의 조건부 표현
```

- 최종 답은 기본적으로 BASELINE_VOTE를 따른다.
- 최종 답이 BASELINE_VOTE와 다르려면 세 조건이 모두 필요하다.
  1. 소수 측 핵심 주장의 인용을 다시 가져와 v로 재확인했다
  2. 다수 측의 반박이 인용 대조나 반대 증거에서 실패했다
  3. 배심원이 독립적으로 소수 측을 지지했다
- 역전은 "기준선 역전"으로 기록하고 근거가 된 증거 ID를 밝힌다.
- 정답이 열린 질문(decision, normative)에서 투표는 판결이 아니라 보고용 기준선이다. 이때도 머릿수는 증거가 아니다.

### 4.3 사전부검

최종안 초안을 사전부검자(초안이 가장 달랐던 참가자, 없으면 배심원)에게 준다.

```
지금은 [해소 시점 또는 1년 뒤]다. 아래 최종 답은 틀린 것으로 확정되었다.
가장 그럴듯한 원인 3가지를 대고, 원인마다 검색으로 확인할 방법을 하나씩 제시한 뒤,
적어도 하나는 실제로 검색하라. 증거는 URL과 원문 인용으로 붙여라.
```

이어서 한 번 더 묻는다: "이 답이 오히려 과소확신일 가장 강한 근거는 무엇인가?"

- 근거 자격을 갖춘 인용이 붙은 원인이나 근거: 최종안을 고치고 "반영"으로 기록한다
- 인용이 없거나 u인 경우: 한 줄 기각 사유와 함께 "기각"으로 기록한다

해소되지 않은 원인은 "S가 관찰되면 결론이 뒤집힌다" 형태의 신호 지표로 바꿔 "이 답이 틀릴 수 있는 조건"에 넣는다.

### 4.4 증거 품질 점검표와 확률

단일 가중 점수를 내지 않는다. 구성요소를 따로 보고한다.

```
검증률     : 최종 답의 팩트 클레임 중 근거 자격을 갖춘 v 인용으로 뒷받침된 비율 (n은 "검토 필요"로 따로 센다)
             (판정을 좌우하는 클레임과 보조 클레임을 나눠 표기)
출처 품질  : 최종 답을 뒷받침하는 인용의 신뢰도 분포 (high/medium/low)
교차 확인  : 판정을 좌우하는 클레임마다 독립 원출처 수 (목표 2 이상, 고위험 3 이상)
원출처 다양성: 마지막 ROUND_STATE의 ORIGIN_DIVERSITY
P0 → P_final: 기준선 확률에서 최종 확률로의 이동과, 이동을 정당화한 증거 ID
```

P_final은 보정되지 않은 값이므로 "UNCALIBRATED"를 붙인다. 판정을 좌우하는 클레임이 반박된 채 최종 답에 남아 있으면 그 부분만 최소로 고친다.

근거 보강: 판정을 좌우하는 클레임 중 독립 원출처가 1곳 이하인 것이 있으면, 예비 예산(검색 5회)으로 보강한다. 이 단계는 토론 라운드가 아니다.

### 4.5 예산

검색 25회, 페이지 가져오기 15회를 넘기지 않는다. 우선순위는 판정 영향, 논쟁 여부, 시간 민감성, 잘 알려지지 않은 사실 순이다. 한 클레임에 쓰는 검색은 최대 2회이고, 두 번째 검색은 첫 검색이 원출처를 1곳 이하로만 찾았을 때만 한다. 상한에 닿으면 남은 클레임은 "예산상 미확인"으로 표시한다. 검색 도구가 요청 한도 오류를 내도 같은 방식으로 처리한다.
