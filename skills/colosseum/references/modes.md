# 질문 유형별 모드

같은 적대적 토론을 모든 질문에 쓰지 않는다. 질문 유형마다 근거가 가장 강한 절차를 쓴다. 워크플로 모드에서는 각 워크플로가 이 절차를 강제하고, 스크립트 모드와 수동 모드에서는 중재자가 이 문서대로 진행한다. 계산은 `scripts/modes.py`(스크립트 모드)나 워크플로의 JavaScript 구현이 맡는다.

forecast, estimate 모드는 실험 단계다. 원인 질문("X는 왜 일어났나")은 경쟁하는 원인 주장을 factual 절차로 토론한다. 아이디어나 이름 짓기처럼 판정할 사실이 없는 요청은 이 스킬로 처리하지 않는다. 데이터 손상과 채점 오류는 고치지만 새 기능은 기술 의사결정 검토(factual, technical, decision)의 검증 뒤로 미룬다. 실험 모드의 보고서는 첫 줄에 "실험 모드: 정확도와 보정이 검증되지 않았다"를 적는다.

| 모드 | 대상 | 핵심 장치 | 근거 수준 |
|------|------|----------|----------|
| factual, technical | 사실 확인, 기술 선택 | 투표 기준선, 인용 검증 토론, 판정 엔진 | 투표와 검증은 강함, 토론 라운드는 조건부 |
| decision | "A를 할까 B를 할까" | 변증법적 탐구(반대 가정 위의 대안), 사전부검 | 동료심사 연구 여러 편, 중간 |
| normative | 가치 판단 | 경험적 쟁점만 판정하고 가치 쟁점은 조건부 지도로 | 관행 수준 |
| forecast (실험) | 미래 사건의 확률 | 기저율, 델파이, 로그오즈 풀링, 예측 기록과 보정 | 통계적 집계는 강함, 델파이는 중간 |
| estimate (실험) | 수치 추정 | 기저율, 델파이, 계열별 중앙값 | 중간 |

## decision

1. 초안과 기준선은 factual과 같다.
2. 대안 구성: 우세한 권고가 기대는 핵심 가정을 모아, 그 가정이 모두 거짓이라고 놓은 위에서 가장 설득력 있는 대안 권고를 세운다. 대안이 옳으려면 무엇이 참이어야 하는지, 어떤 신호가 보이면 갈아타야 하는지 적는다.
3. 경험적 쟁점은 증거 라운드로, 가치 쟁점은 조건부 답으로 보낸다.
4. 최종 답은 권고 형태로 쓰고, 대안으로 갈아탈 신호를 "권고가 뒤집히는 조건"으로 적는다.

## normative

승자를 가리지 않는다. 쟁점 지도를 만들 때 경험적 전제와 가치 전제를 빠짐없이 가른다. 경험적 전제만 증거 라운드로 판정하고, 최종 답은 "X를 Y보다 중시하면 A, 아니면 B" 형태의 조건부 지도로 쓴다.

## forecast, estimate (델파이)

1. 해소 기준과 해소 시점을 먼저 확정한다(확률 예측). 불명확하면 사용자에게 묻는다.
2. 사실 기반 검색에 기저율과 현재 상태를 포함한다. 예측시장이나 집단 예측(Metaculus, Polymarket, Good Judgment Open, Manifold 등)에 같은 기준의 질문이 있으면 그 확률과 원문 구절을 찾는다.
3. 1차: 참가자마다 참조 집단과 기저율을 먼저 정하고, 사안의 특수성으로 조정해 추정한다. 더 높아야 할 가장 강한 이유와 더 낮아야 할 가장 강한 이유를 함께 적는다. 서로의 추정은 보이지 않는다.
4. 델파이 라운드(기본 2회, 상한 3회): 익명 중앙값, 최저값, 최고값과, 중앙값보다 높게 본 쪽과 낮게 본 쪽의 근거를 되먹인다. 참가자는 추정을 유지하거나 수정한다.
5. 수정 제한: 새로 검증된 증거 없이 10%p(추정은 직전 값의 10%)를 넘게 움직이면 그 한도까지만 반영하고 기록한다(`modes.limit_move`). 모든 참가자의 이동이 2%p 미만이면 멈춘다.
6. 집계:
   - 확률: 계열 가중 로그오즈 풀링. 극단화 계수 a는 예측 기록에서 맞춘 값을 쓰되(`CTL forecast fit`), 계열이 둘 이상이고 모든 추정이 0.5의 같은 쪽에 있을 때만 적용한다. 검증된 공개 예측이 있으면 참가자 풀링값과 로그오즈로 반반 섞는다.
   - 추정: 계열별 중앙값의 중앙값(`modes.family_median`). 80% 구간의 하한과 상한도 같은 방식으로 모은다.
7. 사전부검: "해소 시점이 되었고 예측과 반대로 되었다"고 놓고 원인 3가지와 확인 방법을 찾는다.
8. 확률 예측은 `CTL forecast add`로 기록한다. 같은 기록을 다시 넣으면 한 번만 남고, 같은 ID에 다른 내용이면 오류다. 해소되면 `resolve`로 결과를 넣는다. 다른 결과로 덮어쓰려 하면 오류다. 이전 버전의 `forecasts.jsonl`은 `CTL forecast import`로 넣는다.
9. `score`는 저장된 확률을 그대로 채점한다: Brier, 로그 손실, 보정 구간(반개구간, 마지막 구간만 닫힘). 해소된 예측이 20개 이상 쌓이면 `fit`이 극단화 계수를 로그 손실 기준으로 맞추지만, 이 값은 표본 내 적합이므로 실험값이다. 시간 분할 평가가 생기기 전까지 모든 확률에는 UNCALIBRATED를 붙인다.
