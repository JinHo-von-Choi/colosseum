# 사용법

## 질문하기

요청 앞에 호출어(`colosseum`, `팩트체크`, `AI 토론`, `여러 AI에게 물어봐`, `비판적으로 분석`, `다양한 관점`)를 넣고 질문을 쓴다. 질문 유형에 따라 절차가 정해진다.

| 질문 유형 | 예시 | 절차 |
|----------|------|------|
| 사실, 기술 | "PostgreSQL의 SERIALIZABLE 격리 수준은 write skew를 막는가?" | 인용 대조를 거친 근거로 토론 |
| 의사결정 | "폴링을 메시지 큐로 바꿔야 할까?" | 토론에 더해, 반대 가정 위에 세운 가장 강한 대안과 그 대안으로 갈아탈 신호를 제시 |
| 가치 판단 | "핫픽스에도 코드 리뷰를 의무로 해야 하나?" | 사실 전제만 판정하고, 가치 전제는 "X를 Y보다 중시하면 A" 형태로 정리 |
| 예측, 추정 (실험) | "X가 2027년 6월 전에 출시될까?" | 독립 추정, 익명 피드백 라운드, 확률 풀링 |
| 진단 (실험) | "지난주 p99 지연이 왜 두 배가 됐나?" | 경쟁 가설과 근거 행렬 |
| 아이디어 (실험) | "사내 CLI 이름 후보" | 각자 생성, 병합, 블라인드 순위 |

질문을 이렇게 쓰면 검토가 정확해진다.

- 의사결정 질문에는 선택지(현재 방식 유지 포함)와, 선택지를 탈락시키는 제약을 적는다.
- 시간에 따라 바뀌는 사실이면 기준 시점을 적는다. 예: "2026년 10월 기준"
- 예측 질문에는 무엇으로 결과를 판정할지, 언제까지인지 적는다. 빠져 있으면 Colosseum이 묻는다.

## 참가자 고르기

기본 참가자는 3명이다. 설치된 다른 계열의 AI 에이전트가 최대 2자리를 맡고 나머지는 호스트의 기본 모델이 맡는다. 요청에서 바꿀 수 있다.

| 이렇게 쓰면 | 결과 |
|------------|------|
| "codex랑 kimi로" | 두 에이전트를 그 순서대로 먼저 넣는다 |
| "gemini만 써" | gemini와 Claude만 쓰고 다른 외부 에이전트는 넣지 않는다 |
| "외부 에이전트 없이" | 호스트의 기본 모델로 참가자 3명 |

외부 에이전트에 무언가를 보내기 전에, 질문을 받게 될 제공자를 먼저 알려 준다. 자세한 내용은 [외부 에이전트](agents.md)를 본다.

## 보고서 읽기

| 섹션 | 볼 것 |
|------|------|
| 기준선 | `BASELINE_VOTE`와 `P0`. 토론 전의 답이다. 최종 답은 이를 유지하거나, 바꾼 이유를 밝힌다 |
| 라운드별 전개 | 어떤 주장이 공격받았는지, 인용 대조 결과, 입장 변경에 근거가 있었는지. 근거 없는 변경은 `CONFORMITY_FLIP`으로 기록된다 |
| 충돌 판정 | 쟁점별 엔진 판정과, 두 순서로 물은 배심원 판정. "순서 민감"은 양측 순서를 바꾸자 배심원 판단이 달라졌다는 뜻이다 |
| 미해결 쟁점 | 조건부 답. "X가 맞으면 A, 아니면 B" |
| 최종 답변 | 사실 주장마다 출처 ID가 붙는다. `P_final`에는 UNCALIBRATED가 붙는다 |
| 출처 | 인용마다 페이지를 얻은 방식, 대조 결과와 사유, 그 인용이 주장을 뒷받침하는지 |
| 점검표 | 검증된 인용으로 뒷받침된 주장의 비율, 출처 품질, 결정적 주장별 독립 출처 수. 하나로 합친 점수는 없다 |

인용 대조 결과:

| 표시 | 뜻 | 근거로 인정 |
|------|----|-----------|
| `v` | 인용이 페이지에 글자 그대로 있고, 그 문장의 조건을 잘라 내지 않았다 | 인정 |
| `snippet` | 페이지를 가져오지 못했고, 검색 스니펫에 글자 그대로 있다 | 절반 가중치로 인정 |
| `n` | 검토 필요. 비슷하지만 다르거나, 원문 그대로지만 같은 문장의 "if", "only", "except", "경우" 같은 조건을 뺐다 | 불인정 |
| `u` | 원문에 없다. 숫자, 부호, 부정어, 비교 표현("이상"과 "미만" 등)이 바뀌면 항상 `u`다 | 불인정 |

인용이 근거로 인정되려면, 그 인용을 쓴 주장 기준으로 지지 판정도 `full`이나 `partial`이어야 한다. 같은 인용이라도 주장마다 따로 판정한다.

## 결정 기록

의사결정과 기술 질문이면 실행 디렉터리에 `decision.md`(ADR)와 `decision.json`을 만든다. 들어가는 내용:

- 추천안과 그 추천이 성립하는 조건
- 결정적 근거 3개 이내와 인용, 대조 결과
- 반박되지 않은 가장 강한 반론
- 다음 확인 항목: 검토가 필요한 인용, 독립 출처가 하나뿐인 주장, 미해결 충돌
- 기준선과 최종 답의 관계
- 판정 기준을 조금 움직이면 뒤집히는 판정("sensitive" 표시)
- 검토의 한계와 사용한 버전

상태는 `proposed`로 시작하고, 결정은 사람이 한다. 결정을 기록하려면:

```bash
colosseum.py adr --session <id> --run <run_id> --status accepted
```

상태 값: `proposed`, `accepted`, `rejected`, `deferred`, `needs-experiment`

## 가정 바꿔 보기

"출처 E3를 빼면?", "r1.i1.pro.B.0 주장이 입증되지 않았다면?"처럼 묻는다. 모델을 다시 부르지 않고 같은 그래프에서 판정을 다시 계산해, 바뀐 주장과 충돌, 그대로인 것, 변화가 어떤 공격이나 지지 관계를 따라 퍼졌는지 보여 준다. 한 번에 하나만 바꾼다.

```bash
colosseum.py whatif --session <id> --run <run_id> --exclude-evidence E3
colosseum.py whatif --session <id> --run <run_id> --unprove-claim r1.i1.pro.B.0
```

결론이 어느 근거에 기대는지 확인하는 기능이다. 현실에서 일어날 일을 예측하지는 않는다.

## 예측 (실험)

확률 예측은 세션과 상관없이 공유되는 로컬 저장소에 남는다. 결과가 나오면 기록하고 채점한다.

```bash
colosseum.py forecast list
colosseum.py forecast resolve --id <forecast_id> --outcome 1
colosseum.py forecast score
```

`score`는 Brier 점수, 로그 손실, 보정 구간을 보여 준다. 결과가 나온 예측이 20개를 넘으면 `forecast fit`이 풀링용 극단화 계수를 제안한다. 같은 데이터로 맞춘 값이므로 대략적인 추정으로만 본다.

## 중단된 실행

실행은 진행 상황을 디스크에 남긴다. 세션이 중간에 멈추면 이어서 하라고 요청한다. 마지막으로 끝난 단계부터 다시 시작한다. 새 질문은 항상 새 실행으로 시작하고, 이전 실행의 파일은 섞이지 않는다.

```bash
colosseum.py runs --session <id>        # 실행 목록
colosseum.py resume --session <id>      # 현재 실행 이어 가기
colosseum.py restart --session <id>     # 중단하고 새 실행 시작
```

`colosseum.py`는 플러그인의 `skills/colosseum/scripts/colosseum.py`다. 전체 명령은 [레퍼런스](reference.md)에 있다.
